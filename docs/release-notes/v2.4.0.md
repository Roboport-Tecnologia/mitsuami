mitsuami 2.4.0 gives an app a tray icon and keeps it to one instance, so an app that runs in the background can be found again, and a second launch brings the running one forward.

## All platforms

- **`set_tray(TrayIcon)` shows the app's icon in the platform's tray**, with a menu built from the same `Menu` as the menu bar's, until the scope that set it ends. An app that runs without windows needs something to click once its window is closed: the icon brings it back, shows it's still running and holds its Quit. Its title, icon, tooltip and menu follow the app's state, and `tray_shown()` says whether it shows, since a Linux desktop may have no tray.
- **`AppIcon::named(name)` gives an icon from the theme by name**, with `.image(…)` for macOS and Windows, which have no icon theme, and `.dark(…)` for Windows' dark taskbar, because each platform wants its own kind of tray icon and mitsuami passes each the one it understands.
- **`App::single_instance()` keeps an app to one process per user session**: a later launch hands its arguments and working folder to the running app, whose `on_reopen` handlers get them, and exits, so opening a file from the file manager goes to the window already open instead of starting a second copy. The running app's window comes forward first.
- **`NodeRef::present()` brings a window forward**, restoring it if it's minimized, and `Window` takes a `.node_ref(…)` for it. Setting a window's `open` flag does nothing to a window that's open behind other apps' windows, yet every platform's apps bring it to the front when asked for it; `open.set(true); window.present()` shows it either way. Asked while the window is closed, it's done once it opens.
- **`examples/tray.rs` and `examples/single_instance.rs` show them**: the tray example starts with only its icon, opens its window from its menu or a second launch, and lets the window choose how the icon is given.

## macOS (AppKit)

- **The tray icon is a status item in the menu bar**, its image a template that macOS tints for the bar's light, dark and highlighted looks, and macOS keeps where the user dragged it, saved under the app's id.
- **A window opened from the tray's menu comes forward with the app**, because choosing a status item's menu item leaves the app inactive, and the window would otherwise open behind the app in front.
- **A click on the Dock icon reaches `on_reopen`**, which is how macOS apps reopen a closed window.
- **An app that starts with no window isn't activated**, so one started at login doesn't take the focus, and a bundle with `LSUIElement` (a menu bar app) keeps its place out of the Dock.

## Linux (GTK and Kirigami)

- **The tray icon is a StatusNotifierItem**, which Plasma's system tray, waybar and GNOME with the AppIndicator extension show, with its icon from the theme by name, else an image's pixels. Plain GNOME has no tray, and `tray_shown()` stays false there.
- **A window opened from the tray comes forward on Wayland**, because the item takes the activation token Plasma and GNOME's AppIndicator extension hand over before a menu click, and compositors only give the focus with one.
- **Single instance speaks `org.freedesktop.Application`**, so GTK and Kirigami builds of one app find each other, and the window comes forward with the launch's activation token.

## Windows (WinUI)

- **The tray icon sits in the notification area**, with a Win32 menu as Windows 11's own tray menus have, and comes back when Explorer restarts. An `.ico`'s bytes give the image for the screen's DPI.
- **A tray icon's dark variant shows on a dark taskbar**, and swaps when the theme changes, because Windows doesn't recolor tray icons and a monochrome one vanished on a dark taskbar.
- **A later launch hands itself to the running app and exits**, through the Windows App SDK's `AppInstance`, and the running app's window comes forward.
